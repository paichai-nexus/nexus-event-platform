## Safety boundary

- The original checkout and its running rehearsal server were not restarted or modified by the test run.
- The integration runner accepts only loopback PostgreSQL URLs whose database name starts with `nexus_p0b_`.
- `postgres-test` is rejected unless `ALLOW_POSTGRES_TEST_RUNTIME=true`, a 32-character test secret is present, and the process is neither production nor Vercel.
- Each run creates and drops its own temporary database and starts Next.js on an isolated test port.
- No production Supabase URL, key, database, deployment, merge, or push is used.

## Dependency boundary

The staging and production adapters still use Supabase-specific services:

- `@supabase/ssr` for cookie-backed user sessions.
- `@supabase/supabase-js` Auth for login, logout, current-user lookup, and admin readiness.
- PostgREST table queries and RPC calls for repositories.

The P0-B `postgres-test` adapter exercises the same migrations, RLS roles, database functions, repository interfaces, Next.js routes, cookies, and HTTP responses through a local PostgreSQL 17 database. It does **not** emulate or claim validation of Supabase Auth, PostgREST request translation, hosted Realtime, or hosted project configuration.

## Reproduction

Set an isolated PostgreSQL URL template and run:

```sh
P0B_POSTGRES_URL_TEMPLATE='postgresql://postgres:postgres@127.0.0.1:5432/__DATABASE__' \
P0B_ALLOW_ISOLATED_DATABASES=true \
npm run test:p0b
```

The GitHub Actions `application-integration` job provisions PostgreSQL 17 and runs the same scenario without production secrets.
